================================================================================
KỸ THUẬT 1: THỰC HIỆN PHÂN MẢNH NGANG (HORIZONTAL SHARDING)
================================================================================
Mục đích: Chia nhỏ collection bệnh án (hàng triệu bản ghi) ra các server khác nhau.

CÁC BƯỚC THỰC HIỆN TRÊN MONGOS ROUTER (Cổng 27017):

Bước 1.1: Kích hoạt Sharding ở cấp Database
  - Mở mongosh: mongosh --port 27017
  - Gõ lệnh:
      sh.enableSharding("hospital_ehr_db");
  - Kết quả thành công: { ok: 1 }

Bước 1.2: Tạo Index cho Khóa phân mảnh (Bắt buộc phải tạo Index trước khi Shard)
  - Chuyển sang DB:
      use hospital_ehr_db;
  - Tạo compound index trên 2 trường { hospital_branch: 1, patient_id: 1 }:
      db.encounters.createIndex({ hospital_branch: 1, patient_id: 1 });
  - Kết quả: "hospital_branch_1_patient_id_1"

Bước 1.3: Thực hiện lệnh Phân mảnh Collection
  - Gõ lệnh:
      sh.shardCollection("hospital_ehr_db.encounters", { hospital_branch: 1, patient_id: 1 });
  - Kết quả thành công: { collectionsharded: "hospital_ehr_db.encounters", ok: 1 }

Bước 1.4: Kiểm tra trạng thái phân mảnh
  - Gõ lệnh:
      sh.status();
  - Quan sát: Trong danh mục collections sẽ thấy:
      hospital_ehr_db.encounters
        shard key: { "hospital_branch" : 1, "patient_id" : 1 }
        unique: false
        balancing: true


================================================================================
KỸ THUẬT 2: THỰC HIỆN PHÂN VÙNG ĐỊA LÝ (ZONE SHARDING)
================================================================================
Mục đích: Buộc dữ liệu cơ sở Hà Nội chỉ nằm ở Máy A (Shard 1), cơ sở TP.HCM nằm ở Máy B (Shard 2).

CÁC BƯỚC THỰC HIỆN TRÊN MONGOS ROUTER (Cổng 27017):

Bước 2.1: Gán Nhãn (Tag) cho các Server Shard vật lý
  - Gán Shard 1 đại diện cho Vùng Hà Nội:
      sh.addShardTag("shard1ReplSet", "ZONE_HN");
  - Gán Shard 2 đại diện cho Vùng TP.HCM:
      sh.addShardTag("shard2ReplSet", "ZONE_HCM");
  - Kết quả: { ok: 1 }

Bước 2.2: Định nghĩa Dải giá trị (Tag Ranges) cho từng Zone
  - Dải giá trị cho Zone Hà Nội (Tất cả bản ghi có hospital_branch = "HN"):
      sh.addTagRange(
        "hospital_ehr_db.encounters",
        { hospital_branch: "HN", patient_id: MinKey },
        { hospital_branch: "HN", patient_id: MaxKey },
        "ZONE_HN"
      );

  - Dải giá trị cho Zone TP.HCM (Tất cả bản ghi có hospital_branch = "HCM"):
      sh.addTagRange(
        "hospital_ehr_db.encounters",
        { hospital_branch: "HCM", patient_id: MinKey },
        { hospital_branch: "HCM", patient_id: MaxKey },
        "ZONE_HCM"
      );
  - Kết quả: { ok: 1 }

Bước 2.3: Kích hoạt bộ cân bằng tải (Balancer) để di chuyển dữ liệu về đúng máy
  - Gõ lệnh:
      sh.startBalancer();
  - Kiểm tra trạng thái cân bằng:
      sh.isBalancerRunning(); // Trả về true

Bước 2.4: Kiểm chứng kết quả phân vùng địa lý
  - Chèn thử 2 bản ghi: 1 ca ở HN, 1 ca ở HCM:
      use hospital_ehr_db;
      db.encounters.insertOne({
        encounter_code: "ENC-TEST-HN",
        hospital_branch: "HN",
        patient_id: new ObjectId(),
        reason_for_visit: "Thử nghiệm Zone Hà Nội",
        status: "COMPLETED"
      });
      db.encounters.insertOne({
        encounter_code: "ENC-TEST-HCM",
        hospital_branch: "HCM",
        patient_id: new ObjectId(),
        reason_for_visit: "Thử nghiệm Zone TP.HCM",
        status: "COMPLETED"
      });

  - Gõ lệnh kiểm tra vị trí lưu trữ:
      db.encounters.getShardDistribution();
  - Màn hình sẽ in ra:
      Shard shard1ReplSet at <IP_MAY_A>:27018:
        data: ... count: 1 (hoặc số bản ghi HN)
      Shard shard2ReplSet at <IP_MAY_B>:27018:
        data: ... count: 1 (hoặc số bản ghi HCM)
  => Dữ liệu đã tự động chia về 2 máy tính vật lý khác nhau!


================================================================================
KỸ THUẬT 3: THỰC HIỆN BẢN SAO DỰ PHÒNG & TỰ ĐỘNG CHUYỂN VÙNG (REPLICATION & FAILOVER)
================================================================================
Mục đích: Một shard có 1 máy chính (Primary) và 1 máy phụ (Secondary). Khi máy chính tắt,
máy phụ tự động nhảy lên làm máy chính trong 3 giây để hệ thống không bị chết.

CÁC BƯỚC THỰC HIỆN (Thực hiện trên cụm Replica Set):

Bước 3.1: Kiểm tra trạng thái và vai trò của các node trong Replica Set
  - Kết nối trực tiếp vào Shard 1 (Cổng 27018):
      mongosh --port 27018
  - Gõ lệnh xem trạng thái:
      rs.status();
  - Quan sát trong mảng `members`:
      Node nào có `"stateStr": "PRIMARY"` -> Máy nhận lệnh ghi.
      Node nào có `"stateStr": "SECONDARY"` -> Máy sao chép dự phòng.

Bước 3.2: Thêm một máy phụ (Secondary) vào cụm Replica Set (Nếu có thêm máy)
  - Đứng tại node Primary gõ:
      rs.add("<IP_MAY_CON_LAI>:27018");
  - Chờ 5 giây gõ lại `rs.status()` sẽ thấy máy mới gia nhập với trạng thái "SECONDARY".

Bước 3.3: THỰC HÀNH KỊCH BẢN CHUYỂN VÙNG TỰ ĐỘNG (FAILOVER TEST):
  - Bước A: Đang ở node PRIMARY, ép node này từ chức để xem bầu chọn:
      rs.stepDown(60); // Ép Primary từ chức trong 60 giây
  - Bước B: Quan sát con trỏ terminal:
      Con trỏ đổi ngay từ `shard1ReplSet [direct: primary]` thành `shard1ReplSet [direct: secondary]`.
  - Bước C: Node Secondary kia lập tức được bầu lên làm PRIMARY mới.
  => Chứng minh hệ thống có tính sẵn sàng cao (High Availability), không bị gián đoạn.


================================================================================
KỸ THUẬT 4: THỰC HIỆN KIỂM SOÁT GHI AN TOÀN & ĐỌC PHÂN TẢI
================================================================================
Mục đích: Đảm bảo dữ liệu bệnh án sinh tử được ghi an toàn xuống ổ cứng,
và chia tải cho các máy phụ đọc báo cáo để máy chính không bị đơ.

CÁC BƯỚC THỰC HIỆN TRÊN MONGOSH:

Bước 4.1: Thực hành Ghi dữ liệu với mức độ an toàn tối đa (Write Concern)
  - Áp dụng khi Bác sĩ lưu Bệnh án hoặc Đơn thuốc:
      use hospital_ehr_db;
      db.encounters.insertOne(
        {
          encounter_code: "ENC-SAFE-001",
          hospital_branch: "HN",
          patient_id: new ObjectId(),
          doctor_name: "BS. Trần Quốc Tuấn",
          diagnosis: "Đau thắt ngực cấp",
          admission_time: new Date()
        },
        {
          writeConcern: {
            w: "majority",  // Bắt buộc phải đồng bộ sang đa số các máy mới báo thành công
            j: true,        // Bắt buộc phải ghi hẳn xuống ổ đĩa cứng (Journaling)
            wtimeout: 5000  // Hết 5 giây không đồng bộ được thì báo lỗi timeout
          }
        }
      );
  - Ý nghĩa: Nếu máy chủ bất ngờ bị sập nguồn điện ngay sau khi bấm Enter, dữ liệu vẫn 100% không bị mất.

Bước 4.2: Thực hành Đọc phân tải (Read Preference)
  - Khi phòng Kế hoạch Tổng hợp hoặc Giám đốc chạy báo cáo thống kê dịch tễ (truy vấn rất nặng):
  - Ta cấu hình chuyển hướng câu đọc sang máy phụ (Secondary):
      db.getMongo().setReadPref("secondaryPreferred");

  - Sau đó chạy câu lệnh thống kê:
      db.encounters.aggregate([
        { $group: { _id: "$hospital_branch", total: { $sum: 1 } } }
      ]);
  - Ý nghĩa: Câu lệnh này sẽ lấy dữ liệu từ máy phụ (Secondary), máy chính (Primary) hoàn toàn
    rảnh tay để tiếp tục phục vụ các bác sĩ khám bệnh tại phòng khám.

  - Để trả về chế độ đọc mặc định từ máy chính:
      db.getMongo().setReadPref("primary");

KỸ THUẬT 5: THỰC HIỆN GIAO DỊCH PHÂN TÁN ĐA TÀI LIỆU (DISTRIBUTED ACID TRANSACTIONS)
================================================================================
Mục đích: Khi Bác sĩ bấm "Kết thúc khám & Kê đơn": Hệ thống phải cùng lúc
1. Cập nhật trạng thái Bệnh án thành COMPLETED.
2. Tạo Đơn thuốc mới.
3. Trừ số lượng tồn kho trong Kho Dược.
Nếu kho thuốc bị hết hàng -> TOÀN BỘ PHẢI HỦY BỎ (ROLLBACK), không được lưu dở dang!

CÁC BƯỚC THỰC HIỆN (Chạy trực tiếp đoạn mã sau trong mongosh qua cổng 27017):

// Bước 5.1: Khởi tạo phiên giao dịch (Session)
const session = db.getMongo().startSession();

// Bước 5.2: Bắt đầu giao dịch phân tán
session.startTransaction({
  readConcern: { level: "snapshot" },
  writeConcern: { w: "majority" }
});

try {
  const encCol = session.getDatabase("hospital_ehr_db").encounters;
  const rxCol = session.getDatabase("hospital_ehr_db").prescriptions;
  const invCol = session.getDatabase("hospital_ehr_db").pharmacy_inventory;

  const testEncId = new ObjectId();
  const testPatientId = new ObjectId();

  // Thao tác 1: Tạo bệnh án
  encCol.insertOne({
    _id: testEncId,
    encounter_code: "ENC-TX-001",
    hospital_branch: "HN",
    patient_id: testPatientId,
    status: "COMPLETED"
  });

  // Thao tác 2: Tạo đơn thuốc
  rxCol.insertOne({
    prescription_code: "RX-TX-001",
    encounter_id: testEncId,
    patient_id: testPatientId,
    hospital_branch: "HN",
    total_amount: 195000
  });

  // Thao tác 3: Trừ kho thuốc Amlor 5mg đi 30 viên
  const updateResult = invCol.updateOne(
    { drug_code: "DRUG-AML-05", hospital_branch: "HN", stock_quantity: { $gte: 30 } },
    { $inc: { stock_quantity: -30 } }
  );

  // Kiểm tra nếu không trừ được kho thuốc (do hết hàng) thì ném lỗi để Rollback
  if (updateResult.modifiedCount === 0) {
    throw new Error("KHO DƯỢC KHÔNG ĐỦ SỐ LƯỢNG THUỐC ĐỂ CẤP PHÁT!");
  }

  // Bước 5.3: Nếu mọi việc đều tốt -> Cam kết ghi vĩnh viễn (Commit)
  session.commitTransaction();
  print("✔ GIAO DỊCH PHÂN TÁN THÀNH CÔNG: Đã lưu bệnh án, kê đơn và trừ kho thuốc!");

} catch (error) {
  // Bước 5.4: Nếu có lỗi -> Hủy bỏ toàn bộ (Rollback)
  session.abortTransaction();
  print("✖ GIAO DỊCH THẤT BẠI VÀ ĐÃ ROLLBACK: " + error.message);
} finally {
  session.endSession();
}

KỸ THUẬT 6: THỰC HIỆN PHÂN TÍCH & ĐO LƯỜNG HIỆU NĂNG TRUY VẤN (EXPLAIN STATS)
================================================================================
Mục đích: Chứng minh câu truy vấn có đi đúng vào Shard đích (Targeted Query)
hay phải đi phát sóng khắp các máy trên mạng (Scatter-Gather).

CÁC BƯỚC THỰC HIỆN:

Bước 6.1: Chạy truy vấn có chứa Shard Key (Targeted Query - Tối ưu)
  - Câu lệnh:
      use hospital_ehr_db;
      db.encounters.find({ hospital_branch: "HN" }).explain("executionStats");

  - Quan sát kết quả trong JSON trả về:
      + Nhìn vào trường: "queryPlanner" -> "winningPlan" -> "shards"
      + Kết quả: CHỈ xuất hiện 1 shard duy nhất: `shard1ReplSet` (Máy A).
      + Số shard quét: 1 shard.
  => Đây là bằng chứng câu truy vấn được Router bắn thẳng vào đích, không làm tốn băng thông Máy B!

Bước 6.2: Chạy truy vấn KHÔNG chứa Shard Key (Scatter-Gather Query - Chưa tối ưu)
  - Câu lệnh: Tìm theo lý do khám bệnh:
      db.encounters.find({ reason_for_visit: "Thử nghiệm" }).explain("executionStats");

  - Quan sát kết quả trong JSON trả về:
      + Nhìn vào trường: "queryPlanner" -> "winningPlan" -> "shards"
      + Kết quả: Xuất hiện CẢ 2 SHARDS: `shard1ReplSet` VÀ `shard2ReplSet`.
      + Router phải gửi gói tin sang cả Máy A và Máy B, sau đó gom kết quả lại (SHARD_MERGE).
  => Thao tác này giúp bạn giải thích cho thầy cô thấy rõ sự khác biệt giữa câu lệnh
     có dùng Shard Key và câu lệnh không dùng Shard Key!
